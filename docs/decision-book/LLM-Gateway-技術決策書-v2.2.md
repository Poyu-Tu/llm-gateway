# PART 1 — 這個系統在做什麼

## 1.1 解決什麼問題

某間公司讓 200 個員工都能用 AI，三個月後老闆收到帳單：

| 問題 | 具體情況 |
|---|---|
| **帳單看不懂** | 花了 30 萬，但不知道誰花的、花在哪 |
| **沒人管超用** | 某個工程師寫了個測試迴圈，一個晚上燒掉 5 萬 |
| **沒有稽核紀錄** | 有人把客戶個資貼進 AI，事後查不到 |

這三個問題，正好對應本系統的核心價值。

## 1.2 四大功能

| # | 功能 | 白話說明 |
|---|---|---|
| 1 | **智慧路由** | 問題簡單就用便宜模型，問題複雜才用貴的。像叫外送：買瓶飲料不會叫貨車 |
| 2 | **用量計費** | 每一次呼叫都記帳：誰用的、用了多少 token、換算多少錢 |
| 3 | **限流防護** | 每人每月有額度，超過就擋。像手機吃到飽的流量上限 |
| 4 | **稽核紀錄** | 留下時間、來源、內容摘要(去識別化),供資安查核 |

## 1.3 系統邊界(什麼不做)

- ❌ 不自建模型、不做訓練 → 只做「調度與治理」
- ❌ 不做多租戶 SaaS → 定位是企業內部平台
- ❌ 不做知識檢索(RAG)/向量資料庫 → 見 7.9
- ⭕ **選配:極小 agent 當 Gateway 的客戶** → 見 8.2 的 M7,時間夠才做
- ⭕ **對照拆解現成方案(LiteLLM、AWS 原生服務)** → 見 PART 10
- ⭕ **提供輕量 Demo Console(網頁)** → 用於展示內部運作,不是完整產品前端

## 1.4 為什麼不直接用現成的?

> 懂行的人第一個問題通常是:「LiteLLM 或 AWS 自家的服務不就做完了?」
>
> **簡答:** 正式環境我會先評估現成方案。這個專題是把 AI 閘道「拆開來」,親手做出每個環節的最小版本,並把重點放在現成工具不處理的部分:雲端網路隔離、權限、稽核設計。完整對照見 PART 10。

```

    │
    ▼
[1] ALB 收到請求 ────────────────► 健康檢查、路徑判斷
    │
    ▼
[2] Gateway 驗證 API Key ────────► 失敗 → 回 401
    │ 成功
    ▼
[3] Gateway 查 DynamoDB 配額 ────► 超額 → 回 429(限流)
    │ 額度足夠
    ▼
[4] 智慧路由判斷任務複雜度
    │
    ├── 簡單 ──► Claude Haiku (便宜)
    └── 複雜 ──► Claude Sonnet (較貴)
    │
    ▼
[5] 呼叫 Bedrock ────────────────► 走 VPC Endpoint,不出公網
    │
    ▼
[6] 拿到回應
    │
    ├──────► [7a] 立刻回傳給使用者 ✅ (使用者到此結束,不用等記帳)
    │
    └──────► [7b] 丟一筆事件進 SQS
                    │
                    ▼
             [8] Lambda 被 SQS 觸發
                    │
                    ├─ 算成本 (token × 單價)
                    ├─ 寫用量表
                    ├─ 寫稽核 log(內容做 hash,不存原文)
                    └─ 扣減配額
                    │
                    ▼
             失敗 3 次 ──► 進 DLQ(死信佇列),不會靜靜消失
```

**關鍵設計:** 步驟 [7a] 和 [7b] 是**平行**的。使用者拿到答案就走了,記帳在背後慢慢做。

# PART 3 — 每個服務負責什麼

## 3.1 運算層

### Gateway Service(ECS Fargate)
> **角色比喻:** 餐廳前台服務生

| 項目 | 內容 |
|---|---|
| **技術** | Python + FastAPI,打包成 Docker 容器 |
| **位置** | 私有子網,**無 Public IP** |
| **規格** | 0.25 vCPU / 0.5 GB(最小規格) |
| **職責** | 驗證身分 → 查配額 → 智慧路由 → 呼叫 Bedrock → 回傳 → 發計費事件 |
| **對外介面** | `POST /v1/chat`、`GET /health`、`GET /metrics`、`GET /`(Console) |

### Metering & Audit Worker(AWS Lambda)
> **角色比喻:** 後台會計

| 項目 | 內容 |
|---|---|
| **技術** | Python |
| **觸發方式** | SQS 有訊息就自動觸發(事件驅動) |
| **位置** | 同樣掛在私有子網 |
| **職責** | 計算成本 → 寫用量表 → 寫稽核 log → 更新配額 |
| **失敗處理** | 重試 3 次仍失敗 → 送進 DLQ |

### Demo Console(內建靜態網頁)
> **角色比喻:** 引擎的儀表板——不只聽引擎聲,而是直接看轉速表

| 項目 | 內容 |
|---|---|
| **技術** | 單頁 HTML + 原生 JavaScript,由 FastAPI `StaticFiles` 提供 |
| **部署** | **打包在 Gateway 容器內**,不另開 S3 / CloudFront |
| **額外成本** | **$0**(共用現有 ALB 與 Fargate) |
| **路徑** | `GET /` |
| **職責** | 讓「智慧路由的判斷」「即時成本」「配額扣減」「限流被擋」這些內部行為**看得見** |

## 3.2 資料層

### DynamoDB(三張表)

| 表名 | 存什麼 | Partition Key | 用途 |
|---|---|---|---|
| `quotas` | 每個使用者的額度與已用量 | `user_id` | Gateway 同步讀取,判斷是否限流 |
| `usage` | 每一筆呼叫的 token 與成本 | `user_id` + `timestamp` | 報表統計 |
| `audit` | 稽核紀錄(時間、來源、內容 hash) | `request_id` | 資安查核 |

> **為什麼用三張表而不是一張?**
> `quotas` 是「熱資料」,每次請求都要讀,需要極低延遲。
> `usage` / `audit` 是「冷資料」,只有查報表時才讀。
> 分開可以避免大量歷史資料拖慢即時查詢。

## 3.3 通訊層

### SQS(Standard Queue + DLQ)
> **角色比喻:** 餐廳的出單夾

| 項目 | 內容 |
|---|---|
| **主佇列** | `metering-events` — 存放待處理的計費事件 |
| **死信佇列(DLQ)** | `metering-events-dlq` — 處理失敗 3 次的事件會被丟到這裡 |
| **為什麼要 DLQ** | 沒有 DLQ 的話,壞掉的訊息會消失得無聲無息,帳就對不起來 |

## 3.4 AI 模型層

### Amazon Bedrock

| 項目 | 內容 |
|---|---|
| **API** | Converse API(統一介面,換模型不用改程式) |
| **區域** | ap-northeast-1(東京) |
| **模型 ID** | 需加 `apac.` 前綴(跨區推論設定檔) |
| **測試用模型** | Claude Haiku(最便宜,避免測試燒錢) |

## 3.5 網路層

| 元件 | 說明 |
|---|---|
| **VPC** | 自建虛擬網路,10.0.0.0/16 |
| **公有子網** | 只放 ALB |
| **私有子網** | 放 Fargate + Lambda,**無法直接連外網** |
| **ALB** | 唯一對外入口,做健康檢查與路徑路由 |
| **NAT Gateway** | **不使用**(見 PART 7 決策說明) |

### VPC Endpoint 清單

| Endpoint | 類型 | 費用 | 用途 |
|---|---|---|---|
| `bedrock-runtime` | Interface | 計時 | 呼叫 AI 模型 |
| `ecr.api` | Interface | 計時 | ECR 認證與 API |
| `ecr.dkr` | Interface | 計時 | 實際拉取映像檔 |
| `logs` | Interface | 計時 | 寫 CloudWatch |
| `s3` | **Gateway** | **免費** | ECR 映像層實際存放位置 |
| `dynamodb` | **Gateway** | **免費** | 讀寫資料表 |

> ⚠️ **必踩的坑:** `ecr.api`、`ecr.dkr`、`s3` **三個缺一不可**。
> 少任何一個,Fargate 都會卡在 `CannotPullContainerError` 起不來。

## 3.6 支援服務

| 服務 | 用途 |
|---|---|
| **ECR** | 存放 Docker 映像檔 |
| **SSM Parameter Store** | 存放設定值與 metrics token(免費) |
| **CloudWatch Logs** | 應用程式日誌 |
| **CloudTrail** | 記錄「誰對 AWS 做了什麼」 |
| **AWS Budgets** | 花費超過 US$20 寄信告警 |

# PART 4 — 資安設計

> 這是本專案的差異化重點,對應作者的資安維運背景。

## 4.1 核心原則:Zero Egress(零對外連線)

```
一般架構:                        本架構:
                                
私有子網                          私有子網
   │                                │
   ▼                                ▼
NAT Gateway ──► 公開網際網路      VPC Endpoint ──► AWS 內部骨幹
   │                                │
   ▼                                ▼
 AWS 服務                          AWS 服務

月費 ~$45,流量有機會外洩        月費 ~$29,封包從不離開 AWS
```

**生活比喻:** 一般公司大樓需要一扇後門讓員工出去辦事。但如果員工要辦的事都在同一棟大樓的其他樓層,那根本不用開後門——走**內部電梯**就到了,連後門的月租都省了。

## 4.2 六層防護

| 層級 | 措施 |
|---|---|
| **網路層** | 運算節點無 Public IP;Security Group 只開必要 port;無 NAT |
| **身分層** | IAM 最小權限(只給 `bedrock:InvokeModel` + 指定資料表的讀寫,不用萬用字元) |
| **CI/CD 層** | GitHub OIDC 聯邦身分取得**臨時憑證**,repo 內不存長期 Access Key |
| **應用層** | API Key 驗證;`/metrics` 端點另設獨立 token;配額表讀不到時一律拒絕(fail-closed,見 10.3) |
| **前端層** | Console 的 XSS 防護與憑證處理(見 4.4) |
| **資料層** | 稽核 log 只存**內容 hash 與摘要**,不存完整 prompt;入口先偵測個資並遮罩,摘要取自遮罩後的內容,稽核只記錄「偵測到哪一類個資」 |

## 4.3 `/metrics` 端點保護

監控端點會洩漏用量、成本、使用者行為,**不能公開**。

在 ALB 加一條 Listener Rule:

```
IF   path = /metrics
AND  header X-Metrics-Token = <SSM 存的隨機字串>
THEN → 轉發給 Gateway
ELSE → 直接回 403(不轉發到後端)
```

> **面試講法:**
> 「監控端點本身就是攻擊面。我沒有把它跟業務流量放在同一條授權路徑上,而是在 ALB 這一層就用獨立憑證擋掉未授權請求——惡意流量連碰都碰不到後端容器,這是縱深防禦(Defense in Depth)的實作。」

## 4.4 Demo Console 的前端安全

> 多一個網頁 = 多一個攻擊面。加入 Console 後重新做了一輪威脅建模。

| 風險 | 為什麼危險 | 處理方式 |
|---|---|---|
| **API Key 外洩** | 存在瀏覽器可能被其他腳本讀取,或關機後殘留 | 只放 `sessionStorage`,關掉分頁即消失;**不用** `localStorage` |
| **XSS(跨站腳本)** | **模型輸出是不可信輸入**,可能含惡意 HTML/JS | 一律用 `textContent` 渲染,**絕不用** `innerHTML` |
| **任意人存取 Console** | Demo 期間 ALB 是公開的 | Security Group / ALB 規則加 IP 白名單,只允許本人 IP |
| **點擊劫持(Clickjacking)** | 頁面被嵌進惡意 iframe | 回應標頭加 `X-Frame-Options: DENY` |

> **面試講法:**
> 「加上 Console 之後我重新評估了攻擊面。模型輸出對前端來說是**不可信輸入**,所以一律用 textContent 渲染避免 XSS;API Key 只存在 session 層級不落地。多一個介面就要多一輪威脅建模——這是資安工程師的職業習慣。」

```
  /metrics 端點 ◄───── ALB ─────│  Prometheus  │
  (prometheus_client)           │      ↓       │
                                │   Grafana    │
                                └──────────────┘
                                  docker-compose
```

**生活比喻:** 不需要在店裡裝一台 24 小時開機的監控主機(那台主機本身就要電費)。只要在店裡裝好「感應器接頭」,要看數據時把筆電接上去讀就好。

# PART 7 — 決策取捨過程

> 以下記錄「為什麼這樣選」。這一段是本專案與一般教學範例最大的差異。

## 7.1 為什麼不用 NAT Gateway

| | NAT Gateway | VPC Endpoint(本案) |
|---|---|---|
| 月費 | ~$32 + 流量費 | ~$29(4 個 Interface) |
| 封包路徑 | 經過公開網際網路 | 完全在 AWS 內部骨幹 |
| 攻擊面 | 有對外連線通道 | 無 |

**決策理由:** 本系統要連的服務(Bedrock、ECR、CloudWatch、DynamoDB、S3)**全部都有 VPC Endpoint**,沒有任何流量需要真的出去。

> 這不是「因為省錢所以拿掉 NAT」,而是「**因為架構設計得夠聰明,根本不需要 NAT**」。

## 7.2 為什麼拆成兩個服務,而不是一個或五個

**為什麼要拆(生活比喻):**
餐廳只有一個店員,他要接單 → 煮 → 出餐 → 記帳。問題是客人餐點好了,卻要站著等他記完帳才能走。
正確做法:前台專心出餐,單據丟進出單夾;另一個人自己去拿單子慢慢記帳。

**為什麼只拆兩個(而不是把配額檢查也拆出來):**

> 配額檢查在**同步路徑上**,每次請求都要跑。拆成獨立服務等於每次請求多一次網路往返,延遲增加、故障點也增加,但換來的好處(獨立擴縮)在這個流量規模下根本用不到。
> **微服務的拆分依據是「變更頻率」與「擴縮需求」,不是「功能聽起來不一樣」。**

## 7.3 為什麼 Gateway 用 Fargate、Worker 用 Lambda

| | Gateway | Worker |
|---|---|---|
| 呼叫特性 | 每個請求都要跑,需低延遲 | 一天幾百次,可以慢 |
| 執行時間 | 可能等模型回應數十秒 | 幾百毫秒 |
| 選擇 | **Fargate**(常駐,無冷啟動) | **Lambda**(按次計費,幾乎 $0) |

用 Lambda 跑 Gateway 會有冷啟動延遲;用 Fargate 跑 Worker 則是「養一個全職會計,但一天只上班五分鐘」——浪費。

## 7.4 為什麼用 SQS 而不用 Kafka

| | Kafka (MSK) | SQS(本案) |
|---|---|---|
| 費用 | 常駐 broker,月費三位數美金 | 免費層 100 萬則/月 |
| 適用場景 | 多消費者、需重播歷史事件、百萬級/日 | 單一消費者、事件處理完即丟 |

**決策理由:** 本系統的計費事件是「處理完就結束」,不需要重播、也只有一個消費者。SQS 是 serverless 情境下的等價物。

**升級門檻:** 若日均事件量進入百萬級、或需要多個消費者各自重播歷史事件,才換成 MSK / Kinesis。

## 7.5 為什麼用 DynamoDB 而不用 RDS / MongoDB

| 考量 | 說明 |
|---|---|
| **成本** | DynamoDB Gateway Endpoint **完全免費**;RDS 需常駐執行個體,且本帳號 RDS 免費層已過期 |
| **存取模式** | 主要是 `user_id` 單鍵查詢,不需要複雜 JOIN |
| **維運** | 全託管,不用管版本更新與備份排程 |

**什麼時候該換 RDS:** 需要跨表關聯查詢、複雜報表聚合、或有既有 SQL 生態系要整合時。

## 7.6 為什麼用 GitHub Actions 而不用 Jenkins

| | GitHub Actions | Jenkins |
|---|---|---|
| 比喻 | 平台內建的外送系統 | 自己買機車、請司機、顧保養 |
| 基礎設施 | 不用管,有免費額度 | 需要 24 小時開機的 EC2 |
| 維運 | 零 | 自己顧資安更新、備份、崩潰重啟 |

**決策理由:** Jenkins 需要常駐伺服器,直接違背本專案「Zero Egress + 低成本 + 低維運」的核心精神。

**若需 Jenkins 經驗:** 本機用 docker-compose 跑 Jenkins,呼叫同一份 `terraform plan/apply`,證明同一套 IaC 可插進不同 CI/CD 引擎。不上雲。

> 補充:GitLab CI 與 GitHub Actions 概念相同(平台原生、免管伺服器),差別只在語法與綁定平台。學會一個,另一個一兩小時就能上手。

## 7.7 為什麼 Console 內嵌在 Gateway,而不獨立部署

**先講為什麼需要 Console:**
沒有 UI 的話,Demo 只能用 `curl`,畫面是黑底白字。但這個系統最有戲劇性的畫面是「**額度用完 → 被擋 → 回 429**」,以及「路由自動選了哪個模型」——這些用網頁演出來非常直觀。

> **生活比喻:** 你做了一台很厲害的引擎,性能數據都很漂亮。但面試時你只能給對方看 Excel 報表,跟你把引擎裝進車裡讓他踩一腳油門,說服力完全不同。

**三個選項比較:**

| 選項 | 做法 | 額外成本 | 評估 |
|---|---|---|---|
| A. 不做 UI | 純 curl + Grafana | $0 | 技術完整,但 Demo 說服力弱 |
| **B. 內嵌 Gateway**(採用) | FastAPI StaticFiles,走現有 ALB | **$0** | ⭐ |
| C. S3 靜態網站 | 前端獨立部署 | ~$0.05 + 多一組模組 | 架構較正統但過度設計 |

**決策理由:**
1. **零額外 AWS 資源** — 不用新開 S3 / CloudFront,Terraform 不用多寫模組
2. **不破壞 Zero Egress 原則** — 網頁與 API 走同一條 ALB 路徑
3. **FastAPI 原生支援** — `StaticFiles` 掛載只需三行程式碼

**什麼時候該改用選項 C:** 前端變成獨立產品、需要 CDN 加速、或前後端由不同團隊維護時。

## 7.8 為什麼 Demo 不做 HTTPS

**原因:** ACM 憑證免費,但**必須擁有網域**才能簽發(需 DNS 驗證所有權),不想花 NT$400/年。

**補償措施:** Terraform 中把 listener 的 `port` 與 `protocol` **參數化**,切 HTTPS 只需改變數、不改架構。

**生活比喻:** 房子的結構、水電、消防全部到位,只差門口那塊大理石門牌沒裝。門牌是最容易補的,不影響房子評價。

**正式環境做法:** Route53 託管網域 → ACM 申請憑證 → ALB 掛 443 Listener → 加 80→443 強制轉址規則。

## 7.9 其他「不做」項目

| 項目 | 為什麼不做 | 正式環境會怎麼做 |
|---|---|---|
| **AWS WAF** | 每月固定 ~$5 + 每條規則 $1 | 掛在 ALB 前擋 SQLi / XSS / 惡意 Bot,對 `/v1/chat` 設 rate-based rule |
| **多 AZ 高可用** | Interface Endpoint 按「每 AZ 網路介面」計費,雙 AZ 直接雙倍 | 至少 2 AZ,Fargate desired count ≥ 2 |
| **GuardDuty** | 30 天試用後按資料量計費 | Demo 前一週開啟截圖,結束後關閉 |
| **Grafana 上雲** | 常駐運算成本 | Amazon Managed Grafana 或部署於既有 EKS |
| **Ansible / Linux Server** | Fargate 無伺服器容器,沒有 OS 可管,故事會打架 | 另開獨立作品展示地端能力 |
| **多供應商(OpenAI、Gemini 等)** | 要連外部供應商就得開對外連線(NAT),直接違背 Zero Egress;這也是 LiteLLM 最大的價值,本案用不到(見 10.4) | 用 LiteLLM 或 AgentCore Gateway,並評估資料出境與供應商合約 |
| **限速(每秒/每分鐘)** | 本案以「月額度」為主;Demo 只有單一容器,用不到分散式限速 | ALB 前掛 WAF rate-based rule,或用 AgentCore Gateway 的限流 |
| **語意快取** | 需要 ElastiCache 或向量資料庫,屬常駐成本 | 評估 LiteLLM 搭配 Valkey / ElastiCache 的語意快取 |
| **管理後台 / SSO** | 超出「調度與治理」核心,Demo Console 只做展示 | 採用現成方案的管理介面,或整合 IAM Identity Center |
| **RAG / 向量資料庫** | 本專題定位是「調度與治理」(見 1.3);RAG 已在過往專案(面試練習網站)做過,再做一次不會產生新的證明;託管向量資料庫的成本還需另外評估;也會擠壓專題時程 | 若企業要接內部知識庫:在 Gateway 加一層檢索,向量庫依資料量與成本再選型。若指導老師認為有必要,可列為延伸模組討論 |

## 7.10 額度扣減:同步、非同步、預扣

| | 同步扣減(M2) | 非同步扣減(M5 起,採用) | 預扣(不做,升級路線) |
|---|---|---|---|
| 做法 | 拿到模型回應後、回傳前,Gateway 直接扣 | Gateway 只讀額度;Worker 事後依實際 token 扣 | 呼叫前依 `max_tokens` 估算先扣,事後多退少補 |
| 超用空窗 | 小(只有同時進行中的請求) | 稍大(再加上佇列延遲) | 無 |
| 使用者延遲 | 多一次寫入 | 最低 | 多一次寫入 |
| 記帳故障時 | 使用者也受影響 | 使用者照用(M5 故障演練) | 使用者也受影響 |

**生活比喻:** 預扣像加油前先刷卡預授權;非同步像吃完再結帳,偶爾有人多點一道菜,結帳時才發現超過預算。

**實作細節:** 不論哪一種,用量都用 DynamoDB 的原子累加(`ADD`)寫入,多個容器同時寫也不會互相覆蓋,不需要像 LiteLLM 那樣另開 Redis 共享計數(見 10.3)。

**決策理由:** 本系統的額度以「月」為單位,幾筆請求的超用金額極小,換來的是使用者不用等、記帳故障不影響服務。M5 會實測並記錄實際超出多少。

**升級門檻:** 若額度必須是硬上限(例如依合約向部門計費),改成預扣。

## 8.1 AI agent 分層與本專題定位

**生活比喻:** 一般聊天機器人像櫃檯問路的人:你問一句他答一句,不會離開櫃檯。AI agent 像一位管家:你說「週五幫我訂四人晚餐」,他會自己查餐廳、看行事曆、客滿就換一家,最後回報你。核心是一個迴圈:**想 → 動手(用工具)→ 看結果 → 再想**,直到任務完成。

管家花的是你的錢,所以需要預算、門禁與帳本,這就是本專題的「治理層」。agent 做一件事會在迴圈裡連續呼叫模型十幾次,失控時燒錢比一般聊天快得多,這正是治理層存在的理由。

| # | 層級 | 白話 | 怎麼驗證 | 本專題 |
|---|---|---|---|---|
| 1 | 模型串接與紀錄 | 讓 AI 能被呼叫並留下紀錄 | 送一次請求,看到紀錄 | ✅ M1 |
| 2 | 治理(身分、額度、路由、稽核) | 管家的預算、門禁與帳本 | 超額被擋、回 429 | ✅ 主角(M2、M3、M5) |
| 3 | 工具呼叫 | 管家會用電話與行事曆 | AI 要求呼叫工具,結果正確帶回 | ⭕ 選配(M7) |
| 4 | 多步驟迴圈 | 想 → 做 → 看 → 再想 | 任務完成,且有最大步數上限 | ⭕ 選配(M7) |
| 5 | 知識檢索(RAG) | 管家翻公司手冊 | — | ❌ 延伸,不做(見 7.9) |
| 6 | 觀測 | 看管家每天花多少 | Grafana 看到曲線 | ✅ M6 |

### M0.5 拆解 LiteLLM(本機實驗,v2.2 新增)
- **為什麼:** 指導老師指出懂行的人會問「為什麼不用 LiteLLM」。先拆解別人怎麼設計,再決定自己做什麼,比事後辯解有說服力

- **觀察並記錄:**
  1. 拿掉 PostgreSQL 後,預算還有沒有作用

- **安全措施:** 本機用專用 IAM 使用者,只給 Haiku 的 `bedrock:InvokeModel`,實驗結束刪除金鑰
- **驗證:** 截圖 S19、S20(見 11.4)
- **時間/成本:** 約 2～3 小時;只有幾次 Haiku 呼叫
- **產出:** 填入 10.2 對照表的 LiteLLM 欄,並把觀察結果補進 10.3

### M1 最小對話閘道(本機)

- **驗證:** 本機送一次 `POST /v1/chat` 拿到回應;稽核紀錄看得到 hash 與摘要,找不到完整 prompt
- **證明:** 會串接 LLM、有可追溯紀錄(對應指導老師建議的 Step 1)

### M2 身分、額度與個資偵測
- **做什麼:** API Key 驗證、每人額度(`quotas` 表)、超額回 429。本機階段用 DynamoDB Local,並且**暫時由 Gateway 同步扣減額度**(原子累加,見 7.10),M5 再移交給 Worker
- **加做(v2.2):**
  - **fail-closed:** 配額表讀不到時一律拒絕(回 503),不放行。這是拆解 LiteLLM 時學到的反例(見 10.3)
  - **個資偵測:** 送進模型前,用正規表示式偵測身分證字號、手機、Email、信用卡號(加 Luhn 檢查降低誤判),命中就遮罩後再送;稽核表記錄「偵測到哪一類個資」,不記內容。正式環境換成 Bedrock Guardrails
- **驗證:** 連續呼叫直到超額,看到 429;停掉 DynamoDB Local 容器,看到 503 而不是放行;送出含**假**身分證字號的句子,看到遮罩結果與稽核事件
- **證明:** 不只記錄,還能管控,而且壞掉時是安全地壞

### M3 智慧路由、成本與備援
- **做什麼:** 依問題複雜度選擇 Haiku 或 Sonnet;用 token × 單價換算每次成本
- **加做(v2.2):**
  - **備援:** Bedrock 回 `ThrottlingException` 時自動降級到 Haiku,並記錄 fallback 事件;用 pytest mock 模擬,不用真的打到限流
  - **外行版數字:** 用同一組約 20 題,比較「全部用 Sonnet」與「智慧路由」的成本(Sonnet 部分用 token 數 × 單價估算,不實際呼叫),得出 11.2 要用的「省下 X%」
- **驗證:** 一個簡單、一個複雜的問題,選到不同模型;成本數字與手算一致;模擬限流時看到降級紀錄
- **證明:** 具備成本意識
- **注意:** M1～M3 在本機執行,只有 Bedrock 是真的呼叫(小額費用,已含在 6.3 預算內)。為了守住 6.4「全程 Haiku」的省錢原則,Sonnet 只實際呼叫少數幾次,路由邏輯本身用 pytest mock 驗證

### M4 上雲與零對外連線
- **做什麼:** Terraform(遠端 State、OIDC 角色、最小權限)建置 VPC、子網、Security Group、VPC Endpoint;Gateway 打包上 ECR、跑在 Fargate;ALB 作為唯一對外入口
- **驗證:** 雲端跑通與本機相同的流程;Fargate 沒有 Public IP;帳號內沒有 NAT Gateway;`terraform destroy` workflow 實測可以一鍵收掉
- **證明:** 雲端架構與安全設計(Zero Egress)
- **注意:** `ecr.api`、`ecr.dkr`、`s3` 三個缺一不可(見 3.5)

### M5 非同步記帳與稽核
- **做什麼:** SQS + DLQ + Lambda Worker(算成本、寫用量表、寫稽核、更新配額);額度扣減由 Gateway 移交給 Worker
- **驗證(故障演練):**
  1. 手動停用 Lambda 的 SQS Event Source Mapping → 使用者仍正常拿到回應
  2. 重新啟用後事件補記,帳不漏
  3. 刻意讓處理失敗 3 次 → 訊息進 DLQ
- **證明:** 記帳失敗不影響使用者,帳也不會遺失
- **取捨紀錄:** 扣減改成非同步後會有超用空窗,實測記錄超出多少(見 7.10)

### M6 展示與自動化

- **證明:** 可觀測、可重複部署、可現場展示

### M7 (選配)小型 agent
- **做什麼:** 一個只有一兩個工具的簡單 agent 當 Gateway 的客戶,所有模型呼叫都經過 Gateway(Bedrock Converse API 支援 tool use);設定最大步數上限

# PART 10 — 對照拆解:LiteLLM、AWS 原生服務與本專案

> **v2.2 新增。** 起因是指導老師的回饋:外行人看不懂這個作品的意義;懂行的人則會覺得「用 LiteLLM 或雲端廠商自家的服務就好」。這一段要證明兩件事:我拆解過現成方案的設計,也清楚企業 AI 監管的每個環節,而且每個環節都有實作截圖(PART 11)。
>
> 資料查證日期:2026-09-21。雲端服務更新很快,Demo 前一週要再確認一次。

## 10.1 先認識現成方案

**生活比喻:** 想開一間有中央廚房的連鎖店,有三條路:加盟現成品牌(LiteLLM)、租百貨公司美食街的攤位(AWS 全託管服務)、自己從一間小店做起(本專案)。

### LiteLLM

開源的 AI 閘道,用一個統一介面串接上百家模型供應商。以 Proxy 模式部署時由三個零件組成:

| 零件 | 負責 | 比喻 |
|---|---|---|
| Proxy 伺服器 | 驗證虛擬金鑰、路由、呼叫模型 | 櫃檯 |
| PostgreSQL | 虛擬金鑰、團隊、預算、花費紀錄 | 帳本 |
| Redis | 多台 Proxy 共用的限流計數、快取 | 各分店共用的白板 |

拆解重點:
- 預算功能**必須**接 PostgreSQL;官方文件寫明沒接資料庫時,全域預算檢查會被跳過、請求照常放行(fail-open),另外提供 fail-closed 選項
- 開多台 Proxy 卻沒有 Redis,每台各算各的,限額實際會變成兩倍
- 花費是**批次**寫回資料庫,不是每個請求同步寫。跟本案把記帳丟給 SQS + Lambda 是同一個思路
- 第三方部署範本實測約需 0.9 GB 記憶體才能啟動,本案 Fargate 規格是 0.5 GB

### AWS 官方參考架構

AWS 的「Guidance for Multi-Provider Generative AI Gateway」就是把 LiteLLM 部署在 ECS/EKS 上,前面接 WAF 與 ALB,後面接 RDS 與 ElastiCache。

> **本案的骨架(ALB → 私有子網的 Fargate)與官方參考架構相同。** 差別是本案用 DynamoDB 取代 RDS + ElastiCache、用 VPC Endpoint 取代 NAT。

### Amazon Bedrock AgentCore Gateway

AWS 全託管的 AI 流量入口。2026 年 8 月起可依使用者限制請求數、token 數與連線時間,限制單位是每秒或每分鐘。

### Bedrock 與帳務原生功能

| 功能 | 能做什麼 | 限制 |
|---|---|---|
| IAM | 誰能呼叫哪個模型 | 管得到「人」,管不到「用量」 |
| Application Inference Profile + 成本分配標籤 | 在帳單上依部門/專案拆帳 | 事後看帳 |
| AWS Budgets | 超過預算寄信,可觸發動作 | 資料一天最多更新三次,間隔約 8～12 小時,擋不住「一個晚上燒掉」 |
| Model Invocation Logging | 記錄每次呼叫的輸入與輸出 | 存完整內容,與本案「稽核不存原文」衝突 |
| Bedrock Guardrails | 偵測/遮罩個資、擋不當內容 | 按處理的文字量另外計費 |
| Intelligent Prompt Routing | 在同一家族的模型間自動選 | 只限同家族 |

| # | 環節 | 白話 | LiteLLM | AWS 原生 | 本專案 | 截圖 |
|---|---|---|---|---|---|---|
| 1 | 入口與身分 | 門禁卡 | 虛擬金鑰(存 PostgreSQL) | IAM;AgentCore 支援 OAuth / IAM 身分 | API Key + ALB 唯一入口 + IAM 最小權限 | S01、S11 |

## 10.3 從 LiteLLM 學到、直接放進設計的四件事

| # | 在 LiteLLM 看到的 | 本案怎麼做 |
|---|---|---|
| 1 | 沒接資料庫時預算檢查被跳過(fail-open);官方另外提供 fail-closed 選項 | 配額表讀不到一律拒絕,回 503(M2) |
| 2 | 多台 Proxy 要靠 Redis 共享計數,否則限額加倍 | 用 DynamoDB 原子累加,多個容器同時寫也不會互相覆蓋,不需另開 Redis(7.10) |
| 3 | 2026/3/24 PyPI 上的 litellm 1.82.7、1.82.8 被植入竊取憑證的惡意程式,官方判斷起因是 CI 裡使用的 Trivy 遭入侵;官方 Docker 映像因鎖定依賴版本而未受影響 | 本案 CI 也用 Trivy:所有 Action 釘 commit SHA、依賴用含 hash 的 lock 檔、映像鎖定版本(M6) |
| 4 | 2026 年也公布過花費紀錄意外記到機密 header、Proxy SQL injection、驗證繞過等問題 | 稽核只存 hash 與摘要,不記 header 與 API Key。閘道握有所有模型的鑰匙,是高價值目標;不論自建或採用,都要有修補與掃描流程 |

> 第 4 點不是說 LiteLLM 不安全。自建的程式一樣會有漏洞,差別在於:採用現成方案要追它的公告並即時更新;自建要自己做掃描與測試。兩條路都要有人顧。

## 10.4 為什麼自建,而不直接用?

| 選項 | 做法 | 適合誰 | 本專題為什麼不採用 |
|---|---|---|---|
| A. LiteLLM 自架 | 官方映像 + PostgreSQL + Redis,部署在 ECS(即 AWS 官方參考架構) | 要接多家模型、需要現成管理後台的企業 | 最大價值是多供應商,但本案只用 Bedrock,接外部供應商就得開對外連線,違背 Zero Egress;預算功能需常駐 PostgreSQL(本帳號 RDS 免費層已過期);記憶體需求約為本案規格兩倍 |
| B. AgentCore Gateway | AWS 全託管,依使用者限流 | 已在 AWS 上跑 agent 的團隊 | 限流單位是每秒/每分鐘,屬於「限速」;8 月公告沒有提到每人月額度與部門成本報表;全託管看不到內部,無法當作拆解學習的對象 |
| C. Bedrock 原生功能拼裝 | IAM + Inference Profile 標籤 + Budgets + Invocation Logging + Guardrails | 小團隊,只需要事後看帳 | Budgets 只能事後告警、擋不住即時超用;Invocation Logging 存完整內容,與稽核設計衝突 |
| **D. 自建最小 Gateway(採用)** | FastAPI + DynamoDB + SQS / Lambda | 學習與展示每個環節 | — |

**結論:**
- **正式環境:** 我會先評估 A 或 B,不建議從零自建。
- **這個專題選 D,理由三個:**
  1. **用不到最大價值:** 本案只接 Bedrock,多供應商用不到;要用就得開對外連線
  2. **成本:** A 需要常駐資料庫與更大的運算規格,違背 6.1「時鐘只在工作時轉」
  3. **學習目的:** 自己做出每個環節的最小版本,才看得懂現成工具的設定、限制與失敗模式;10.3 的四件事就是證據
- **可替換性:** 本案的 Terraform、網路、CI/CD 與 AWS 官方參考架構同一骨架。企業若改用 LiteLLM,換掉容器映像並補上資料庫,其餘可以沿用。

**生活比喻:** 我不是要取代市售的輪子,是拆一個輪子,看懂輪軸、軸承、胎壓各自在做什麼。正式上路我會買輪子,但我知道怎麼檢查它、它會在哪裡壞。

## 10.5 面試講法

> 「我評估過 LiteLLM、AgentCore Gateway 和 Bedrock 原生功能。正式環境我會先選現成的;這個專題我刻意做最小版本,因為我要看懂每個環節。拆解 LiteLLM 時我發現,它沒接資料庫時預算會直接放行,所以我的配額設計成讀不到就拒絕;它今年也因為 CI 裡的 Trivy 被入侵而發生供應鏈事件,我的 CI 同樣用 Trivy,所以每個 Action 都釘在固定版本。另外,這些現成工具都不處理網路隔離,所以我把重點放在 Zero Egress。」

## 11.5 截圖規範

- **存放:** repo 的 `docs/screenshots/`,檔名照 11.4
- **遮蔽:** AWS 帳號 ID、API Key、IP、ARN 中的帳號段。這是資安習慣,也避免作品公開後外洩
- **說明:** 每張截圖旁寫一句「這張證明什麼」
- **時機:** 每關驗證通過當下立刻拍。事後為了補截圖重建環境,既花時間也花錢(見 8.3)
