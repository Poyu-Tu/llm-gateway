## 0. 三十秒版（給非技術讀者）

- **做出了什麼：** 「AI 收費櫃檯」收完錢不再自己記帳，而是把帳單放進「出單夾」（SQS），由後台會計（Lambda Worker）去記。會計請假、櫃檯當機，帳單都還在出單夾裡，**一筆都不會掉**。
- **三本帳一起寫：** 會計記帳時，用量明細、本月累積、稽核紀錄三本**要嘛全寫、要嘛全不寫**；同一張帳單送來兩次，只記一次。
- **出單夾壞了也照樣營業：** 帳單放不進出單夾時，櫃檯照樣把答案給客人，然後自己把帳記好、在交班本留一行。
- **雲端實際演了一次消防演習：** 讓會計停工、讓櫃檯當機、丟一張看不懂的帳單、把出單夾整個拿走，全部照設計運作，最後 4 分鐘拆光。
- **誠實的弱點：** 額度是「軟上限」：會計停工那段時間，示範帳號多用了 27.4% 才被擋下（這是不做預扣的代價，已量化）；上雲第一次就撞到一個本機和模擬器都驗不出來的權限設定；公開的部署日誌曾印出本人的 IP（已刪除、已修）。
- **花費：** 上雲演練約 1 小時 32 分，初估約 US$0.2（Cost Explorer 尚未進帳，待補）；OpenAI 約 US$0.0013；投入約 19 小時。

## 1. 為什麼做

**M5 要證明：記帳失敗不影響使用者，帳也不會遺失。** 決策書 10.2 的第 6 環節（計費與歸屬）要的是「每一筆都算得出來、對得上」；M0.5 拆 LiteLLM 時看到它在寫帳前當機就永久掉帳（E26），M4 的同步記帳又有「扣款與稽核同時失敗就只剩一行日誌」的缺口。M5 就是補這兩個洞。

M0～M4 的經驗，讓 M5 的設計對著四件事做：

1. **錢付出去之後，就不能拒絕回答。** 記帳路線壞了，使用者照樣拿到回答；問題留給後台處理（M4 稽核寫不進去時的做法，延伸到 SQS）
2. **「至少送到一次」不是「剛好一次」。** SQS Standard 會重送，備援路線也可能重複寫，帳一定要能去重
3. **雲端的錯很多是安靜的**（M4 第 4 節）。所以每個設計都要有一個上雲後「看得到它做對」的驗證步驟
4. **按小時計費的資源要一次演完、當天拆。** 七個故障演練排成一次上雲做完

**生活比喻：** 餐廳加了出單夾和一位後台會計。外場把單夾進出單夾就上菜；會計拿單記三本帳（明細、會員卡累積、紀錄簿），同一張單掃兩次只記一次；字跡糊掉的單試五次還看不懂，就放進問題抽屜；出單夾卡住時，外場自己記帳、在交班本寫一行。

## 4. 最重要的一點：本機、模擬器都過了，雲端還是要演一次

M4 學到「雲端的錯很多是安靜的」。M5 往前一步：**有些錯，在雲端之外根本沒有地方可以看到。** 這一關在動手前做了四道檢查：本機 380 個測試、`terraform validate`、權限模擬器 6 組、`validate-policy`，全部過了。上雲第一次 `apply`，Worker 還是建不起來。

| 哪一道 | 驗的是什麼 | 驗不到什麼 |
|---|---|---|
| 本機測試 | 程式邏輯；DynamoDB Local 的交易 | IAM（DynamoDB Local 不檢查權限）、真的 SQS 與 Lambda |
| `terraform validate`／`plan` | 參照找得到、格式對 | 值對不對（`handler` 少一段、名字當 ID）|
| 權限模擬器 | 身分政策的邏輯：這張證能開哪些門 | 動作名稱拼錯（照字面比對）、**誰能借這張證** |
| `validate-policy` | 動作名稱存不存在、文法 | 該不該開這扇門、**誰能借這張證** |
| **上雲演練** | 全部接起來的樣子 | — |

Worker 信任政策上的 `aws:SourceArn`，文法完全正確、意圖也合理（「只有這個函式能借這張證」），四道檢查都不看它。CloudTrail 只看到「借證成功、建網卡的預演說會成功」，之後就沒有下文。最後是查 AWS 文件才知道：替 VPC 函式建網卡、從 SQS 拉訊息這兩件事，Lambda 不會帶來源函式的 ARN。

**生活比喻：** 員工證做好了，門禁測試機（模擬器）說每扇門都開得了，校對員（`validate-policy`）說證上的字都沒拼錯。結果第一天上班，管理處不讓代辦員拿這張證去幫會計裝座位，因為證背面寫著「只有拿著會計名牌的人能借」，而代辦員身上沒有名牌。證背面的規定，測試機和校對員都不看。

**帶到後面的做法：**

1. 每一道檢查都寫清楚「它驗不到什麼」，上雲演練就照那張清單排
2. 演練的第 0 步永遠是「正常走一次、看下游的日誌」，不是看 `apply` 成功
3. 信任政策、資源政策這類「誰能用」的設定，改了就要上雲驗

## 5. 挫折與解法

| 卡在哪 | 原因 | 怎麼解決 | 學到什麼 | 證據 |
|---|---|---|---|---|
| 填空寫成 `period, str` | 少一個冒號，Python 不報錯，多出第四個參數 | 讀程式時抓到 | 型別標註寫錯會變成參數 | E130 |
| `save_charge()` 寫成 `raise` | 送成功時沒有正在處理的錯誤 | 改 `return` | 每一次送成功都會回 500 | E134 |

## 6. 新的取捨決定

M5 期間的定案記在證據紀錄，整理成決策書 v2.11 的 20 項待改與 12.12 的新定案（D98～D122）。影響最大的六個：

1. **SQS 送不進去時，回答照給、Gateway 自己記帳。** 不選回 503：錢已經付給 OpenAI，使用者重試會再花一次。不選只印日誌：雲端最可能的故障是設定錯誤，會連續發生，額度整段失效。代價：Gateway 的寫入權限拿不掉、兩條記帳路線
2. **三本帳一個交易、單號去重，Worker 與備援共用同一支函式。** 不選不防重複：多扣的錢記在使用者身上。代價：交易寫入費用 2 倍（Demo 不到一分錢）
3. **預扣不做，額度是軟上限。** 不選完整預扣：照最壞情況扣，示範帳號一次都叫不了；退款是新故障點。代價：實測 Worker 停工時超扣 27.4%，最壞情況強模型一次約 US$0.028
4. **Worker 放私有子網，出口只到 DynamoDB。** 不選放 VPC 外：繞過 DNS 防火牆。代價：拆的時候要等網卡收回（實測約 1 分鐘）
5. **DLQ 失敗 5 次、Lambda 逾時 20 秒、隱藏 120 秒。** 不選 3 次：比 AWS 建議少，限流時正常的帳也可能進 DLQ。代價：壞訊息約 10 分鐘才進 DLQ
6. **Worker 信任政策不加來源條件。** 不選保留：Lambda 建不起網卡。代價：少一層「只限這個函式」的保險；靠 `iam:PassRole` 守

## 7. 限制（誠實記錄）

**記帳**

- **額度是軟上限：** Worker 停工或延遲的那段時間不會擋，實測超扣 27.4%
- **「拿到 OpenAI 回答之後、送 SQS 之前」Gateway 當掉：** 那一筆沒有記帳也沒有稽核；只有幾十毫秒，靠 M6 與供應商對帳補
- **SQS 與備援都失敗時：** 只剩一行 `audit_write_failed` 日誌，補收是手動的
- `audit_write_failed` 有兩種意思（沒花錢的稽核寫不進去／花了錢兩條都失敗），要看欄位才分得出來
- DLQ 只有人工搬回，沒有自動重送

**驗證範圍**

- `charge_queue_failed` 告警（5 分鐘 ≥ 3 筆）沒有實際響過，演練只聊一次
- 高流量下 Worker 的同時執行數、交易衝突沒有測；演練的流量是個位數
- 雲端交易被取消時的錯誤格式只走過「重複」以外的路（第 0 步正常寫入）；「已經記過」那條在雲端沒有實際觸發
- 延遲只量了第 0 步一次（約 6 秒入帳，含冷啟動）

**權限與部署**

- Worker 信任政策少了來源條件，靠 `iam:PassRole`
- destroy 日誌的 IP 過濾要下一次 destroy 才算實測
- 個人電腦的 Terraform 還是 1.16.5
- 雲端 alice、bob 各有 M4、M5 兩把有效的 Key（seed 不停用舊的）

**花費**

- Cost Explorer 在 10/23 晚上還沒進帳，AWS 實際金額待補
