### 主影片 02｜問題與動機

先看一個情境。公司開放兩百位員工使用 AI，三個月後帳單來了：總額看得到，卻不知道是誰花的。有人寫錯一個測試迴圈，一個晚上就把預算燒掉。有人把客戶資料貼進去，事後查不到紀錄。成本歸屬、用量管控、稽核，這是企業把 LLM 用起來之後才會遇到的三個治理缺口。

### 主影片 03｜解法與定位

- **標題：** 在使用者與模型之間，裝上水表和限流閥
- **預估：** 118 字，約 32 秒
- **畫面順序（之後做動畫用）：** 由左至右：使用者、閘道、模型；接著六個步驟逐一亮起；最後出現定位句。

我的做法，是在使用者和模型之間放一個閘道。公司共用 AI，就像整棟大樓共用一條水管卻沒有分表，我做的是替每一戶裝上水表和限流閥。每一次呼叫都要先過這一關：確認身分、檢查額度、遮掉個資、選模型、記帳、留稽核。我的定位是雲端工程師，負責 LLM 上線之後的治理，而不是模型本身。

實際跑起來是這樣。第一，簡單的問題交給便宜的模型，複雜的才用強模型，兩者單價差二十倍。第二，每個人每個月有額度，用完就擋下來；額度資料如果讀不到，系統選擇拒絕，而不是放行。第三，內容裡如果有信箱、手機、身分證字號或信用卡號，會先換成類別標籤，才送出去。這些規則都是先寫測試、確認它失敗，再寫功能。

有人會問，為什麼不直接用現成的 LiteLLM？所以動手之前，我先把它拆開來測，發現兩件事。第一，內建價格表沒有我要用的新模型，呼叫照樣成功，花費卻記成零，預算等於沒設，而且沒有任何警告。第二，它是先回答、十幾秒後才記帳；我在回答後不到一秒把它強制關掉，那筆帳就永遠不見了。回頭看，我自己的設計也有同樣的洞，所以我改成先確認帳進了佇列，才回答使用者。

### 技術版 01｜定位與範圍

- **預估：** 83 字，約 23 秒

技術版先交代範圍。AI 應用可以分成六層，我做的是第二層，治理：身分、額度、路由、計費、稽核，再加上網路邊界。知識檢索這次不實作，接入方式放在最後說明。不自建模型、不做多租戶，也不同時接多家供應商。

### 技術版 02｜系統架構

- **標題：** 同步路徑與非同步路徑分離，對外只有一個出口
- **預估：** 94 字，約 26 秒
- **畫面順序（之後做動畫用）：** 先出現使用者到 Gateway 的同步路徑，再出現右側三條去向，最後出現 SQS 到 Lambda 的非同步路徑。

架構分成同步和非同步兩條路。同步這條，請求從 ALB 進來，到私有子網裡的 Fargate，依序做驗證、查額度、遮罩、路由、呼叫模型。非同步這條，計費事件進 SQS，由 Lambda 計算成本、寫用量與稽核。對外只有 NAT 一個出口，DynamoDB 和 S3 走 Gateway Endpoint。

### 技術版 03｜系統架構｜請求流程

- **標題：** 回應之前，計費事件已在佇列
- **預估：** 77 字，約 21 秒
- **畫面順序（之後做動畫用）：** 步驟 1 到 8 逐一出現，第 7 步高亮；最後出現非同步的第 9 步。

一次請求有九個步驟。重點在第七和第八步的順序：先確認計費事件進了佇列，才回應使用者。額度檢查排在呼叫模型之前，超額的請求回 429，不會產生費用。資料庫讀不到時回 503，不放行。

動手之前先拆解 LiteLLM。選版用冷卻期規則，不追最新版；用 digest 驗證 cosign 簽章；官方範例的七項不安全預設值逐項修正；然後做破壞測試：斷網、關資料庫、不設資料庫、預算設零、強制終止。AWS 自家服務因為帳號的 Bedrock 被封鎖，只做文件對照。

### 技術版 05｜現成方案拆解｜發現一

- **標題：** 價格表沒有的模型，花費記為 0，預算失效
- **預估：** 99 字，約 27 秒
- **畫面順序（之後做動畫用）：** 左側因果鏈三步依序出現，右側出現資料庫查詢結果，最後出現本案設計。

第一個發現。為了不在啟動時下載未驗證的資料，我關掉線上價格表，改用內建的。結果內建表沒有我要用的平價模型，呼叫成功、token 有記，花費是零，預算上限永遠不會觸發。所以我的設計是：單價放在版本庫的設定檔，沒有單價的模型直接拒絕。

### 技術版 06｜現成方案拆解｜發現二

- **標題：** 寫帳前當機，該筆帳永久遺失；據此修正計費事件順序
- **預估：** 105 字，約 29 秒
- **畫面順序（之後做動畫用）：** 先出現終端機紀錄，再出現修正前後的流程對照。

第二個發現。LiteLLM 的花費先放在記憶體，七到十四秒後才批次寫入。我在回應後零點八秒送出 SIGKILL，重啟後明細和累計都沒有補回。我原本的流程把回應和送事件畫成平行，一樣會掉帳，所以改成先入佇列再回應，代價是每次多十幾毫秒。這個測試只做了一次。

### 技術版 09｜現成方案拆解｜自建的理由

- **標題：** 正式環境先評估現成方案；本專題自建最小版本
- **預估：** 102 字，約 28 秒
- **畫面順序（之後做動畫用）：** 表格逐列出現，D 列高亮；右側圖表長條由下往上長出。

所以為什麼自建？正式環境我會先評估現成方案。這個專題選擇自建，是因為 LiteLLM 的預算功能需要常駐資料庫，AgentCore 的限流單位是每秒每分鐘、沒有月額度，Bedrock 原生功能只能事後告警。記憶體的對照只說明功能少的時候需求較低，兩者功能並不對等。

### 技術版 10｜身分與額度

- **標題：** 額度以美元計；讀不到額度時拒絕，不放行
- **預估：** 116 字，約 32 秒
- **畫面順序（之後做動畫用）：** 表格逐列出現，接著下方三張驗收畫面由左至右出現（S01 的 401、S02 的 429、S03 的 503）；可切到對應的錄影。

身分與額度。API Key 只存 SHA-256 雜湊，錯的 Key 一律回同樣的 401。額度以美元計，存成 micro-USD 整數。額度放在使用者層級，已用量一個月一筆，換月不用任何人動手。超額回 429 並告知何時恢復；資料庫讀不到時回 503，不放行。這個做法會小幅超扣：驗收時額度一千，實際用到一千一百二十。

### 技術版 11｜內容防護

- **標題：** 入口個資遮罩：四類規則完成，順序由測試鎖定
- **預估：** 133 字，約 36 秒
- **畫面順序（之後做動畫用）：** 表格出現後，右側出現測試失敗的訊息，強調第二行的網域外流。講到驗收時切到 S04 的錄影。

內容防護。四類個資用規則比對，換成類別標籤。信用卡要過 Luhn 檢查才遮，身分證不驗檢查碼，依據是漏遮的代價和誤遮的機率。遮罩的先後順序由測試鎖定：我把順序對調過一次，確認測試會失敗。驗收時我請模型原樣重複一句含假身分證字號的話，它重複出來的是標籤。這是規則版本，正式環境會換成託管的內容防護服務。

### 技術版 12｜路由與成本

- **標題：** 規則式路由；成本以回應的 usage 計算
- **預估：** 104 字，約 28 秒
- **畫面順序（之後做動畫用）：** 先出現兩個模型卡片與中間的規則，再出現下方三點。M3 驗收後加入 S05～S07。

路由與成本。規則是輸入達三百字或含指定關鍵字就用強模型，其餘用便宜模型，使用者不能自己指定。成本以回應的 usage 計算，思考 token 算在輸出。強模型被限流時降級一次；供應商預算用完時不降級，直接回 503。這部分在 M3 實作，門檻會用測試集調整。

### 技術版 13｜計費與稽核

- **標題：** 稽核只存 HMAC 與遮罩摘要，原文不落地
- **預估：** 60 字，約 16 秒
- **畫面順序（之後做動畫用）：** 左側三點依序出現，右側放 M1 驗收畫面。

稽核。雜湊用 HMAC-SHA256，因為短句的一般雜湊可以用字典還原。摘要固定先遮罩、再截斷前五十字。原文只存在 Gateway 的記憶體，不進佇列、資料庫和應用日誌。

### 技術版 14｜網路邊界

- **標題：** Zero Egress 改為受控出口：只有一個出口，而且有管控
- **預估：** 90 字，約 25 秒
- **畫面順序（之後做動畫用）：** 上方轉折流程由左至右出現，接著出現 AWS Support 回覆，最後出現選項比較表。

網路邊界。原本的設計是零對外連線，因為 Bedrock 被帳號層級封鎖，改用 OpenAI 之後一定要有出口。我選 NAT 加 DNS Firewall 放行清單，安全群組只開 443。這個做法擋不住直接用 IP 連線，Network Firewall 可以，但五十小時要多十七美元。

### 技術版 15｜身分與金鑰管理

- **標題：** 供應商端也做最小權限、硬性上限與短期金鑰
- **預估：** 99 字，約 27 秒
- **畫面順序（之後做動畫用）：** 五道防線逐列出現；右側 AWS 端分成已完成與待完成兩組。

身分與金鑰。OpenAI 這一端做了五道防線：預付不自動加值、專案硬性上限、模型白名單、金鑰只開 Chat Completions、服務帳號三十天到期，白名單外的模型實測被擋。AWS 這一端已完成 MFA、移除長期金鑰和預算告警；最小權限的角色和 OIDC 在上雲時完成。

### 技術版 16｜供應鏈與 CI/CD

- **標題：** 套件、映像與版本庫的基線已建立
- **預估：** 75 字，約 20 秒
- **畫面順序（之後做動畫用）：** 左側已完成的項目逐一出現，右側為待完成項目。M6 加入 Trivy 攔截的畫面（S16）。

供應鏈。已經做到的是：Python 套件設冷卻期，基底映像鎖 digest，容器以非 root 執行，建置內容用白名單，版本庫開啟推送保護並禁止強制推送。CI 的弱點掃描和 OIDC 部署排在後面的階段。

### 技術版 17｜驗證、觀測與展示

- **標題：** 每個驗收條件先寫成測試；故障以演練驗證
- **預估：** 71 字，約 19 秒
- **畫面順序（之後做動畫用）：** 三欄依序出現。此頁於 M5、M6 驗收後換成實際畫面。
